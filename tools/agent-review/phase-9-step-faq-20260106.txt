## Project Basics

- Language: Python (3.10+)
- This repo is NOT greenfield; always extend existing code.
- Build/test entry points are defined in `pyproject.toml`, `Makefile`, or `scripts/`.
- Read `README.md` first for setup and usage.
- Type checking is strict; avoid `Any` and generic container types.
- Ruff compliance is required (do not auto-format unless explicitly requested).

## Relationship to PyPNM (pypnm-docsis)

- PyPNM-CMTS consumes PyPNM (pypnm-docsis) as a dependency.
- SNMP logic is authoritative in PyPNM and must NOT be re-implemented here.
- If a required SNMP capability is missing, implement it in PyPNM and consume it here.
- Before proposing or making any PyPNM changes, explicitly tell the user what would be added/changed and why.
- PyPNM must not regress; call out any PyPNM-side changes explicitly.
- Never push branches directly to PyPNM `origin`; follow the PyPNM release process.

## Repo Conventions

- PyPNM-CMTS services one CMTS instance.
- Scaling is achieved by Service Group (SG), not by global CM count.
- Standalone (Option-A) is the default architecture.
- Kubernetes is a future deployment model; do not implement K8 APIs unless explicitly requested.
- No database. Persistence is filesystem-based only (JSON / JSONL).

## Documentation

- Docs must follow the existing repo docs layout and conventions.
- Update docs alongside code changes (choose the correct location by inspecting the existing docs tree; do not invent parallel structures).
- Do not modify `mkdocs.yml` or navigation unless explicitly requested.
- Markdown must render correctly in both MkDocs and GitHub.
- No emojis in documentation.
- Use generic placeholders:
  - MAC: `aa:bb:cc:dd:ee:ff`
  - IP: `192.168.0.100`
- Emojis are allowed only in `pypnm-cmts` CLI output and `install.sh`; they are prohibited everywhere else.
- When adding new terms or acronyms, update `docs/definition/index.md` and keep entries in alphabetical order.
- After completing a task, create a single “agent review” file that concatenates the full contents of all files changed in that task (path and naming should follow existing repo practice).
- Always regenerate the agent review bundle after any subsequent edits so it reflects every changed file.
- When an error is fixed, add or update a FAQ entry with the error and resolution, and add a TODO entry noting the FAQ update requirement.

## Configuration

- `system.json` is the single source of truth.
- New configuration namespaces must be implemented as Pydantic BaseModels.
- BaseModels must use one-line `Field(..., description="...")`.
- Operators should not be required to tune internal orchestration behavior.
- All PyPNM-CMTS type aliases live in `src/pypnm_cmts/lib/types.py`. Add new types there only.
- Always check `pypnm.lib.types` before creating new types in PyPNM-CMTS.
- All ID-like fields (election_name, leader_id, owner_id, sg_id, etc.) must use type aliases from `src/pypnm_cmts/lib/types.py`.
- Avoid generic `str` for semantic identifiers or paths in public models and APIs; use an existing semantic type or add a new alias in `src/pypnm_cmts/lib/types.py`.
- PyPNM `ServiceStatusCode` is the shared enum and must remain <= 9999.
- PyPNM-CMTS `CmtsStatusCode` starts at 10000 to prevent collisions.
- Do not renumber existing codes; if codes change, update both repos or migrate to a shared dependency.
- When working with MAC or inet strings, validate using `MacAddress()` or `Inet()` instead of assuming `str(...)` formatting is valid.
- All SNMP calls must be wrapped in try/exception handling.

## Timestamp Conventions

- All stored timestamps are epoch seconds.
- Convert to ISO-8601 only at display or external response boundaries.
- Rationale: compact storage, easy comparisons, stable serialization.

## Coding Guidelines (Strict)

- No generic container imports (`Dict`, `List`, `Tuple`, `Union`).
  Use built-in types and `|`.
- Avoid `Any` unless unavoidable; isolate and justify its usage.
- Every function argument must be annotated.
- Avoid `None` returns; prefer empty values unless `None` is semantically required.
- Avoid magic numbers; use named constants.
- Prefer `BaseModel` over raw dicts for public/stateful structures (state, configuration, coordination).
- dicts are allowed only for short-lived internal glue logic.
- Prefer classes with static methods over standalone functions.
- Public methods MUST have detailed docstrings.
- Private methods may have minimal docstrings.
- Avoid method-level debug logs.
- Do not add Ruff ignores (`# noqa`, `# ruff: noqa`). If an ignore is needed, ask for permission first.
- Logging pattern in classes:

  ```python
  self.logger = logging.getLogger(f"{self.__class__.__name__}")
````

* Prefer `match/case` over long if/else chains.
* No one-line if statements (E701).
* Preserve all existing whitespace and alignment.
* Never auto-format or re-align code.
* Do not enforce snake_case; keep existing naming conventions as-is.
* Do not use `time.sleep()` in FastAPI request paths; it blocks worker threads and reduces throughput.
* Default to `asyncio.sleep()` when polling is required in async code.
* If code is synchronous and would otherwise sleep in a request path, redesign to avoid sleeping or move the wait to background/async paths.

## FastAPI Guidelines

* FastAPI routes in PyPNM-CMTS must follow PyPNM (pypnm-docsis) route patterns:

  * class-based router wrapper
  * APIRouter prefix/tags
  * `__routes()` (or equivalent) registration method
  * shared response envelope (e.g., `FAST_API_RESPONSE`) where applicable
  * response models and router export conventions
* Prefer POST for payload submission, non-idempotent actions, or complex filters.
* Allow GET for read-only, idempotent, lightweight lookups (health, readiness, version, status).
* All request/response bodies must be Pydantic BaseModels.
* Reusability is mandatory:

  * Define shared models under `src/pypnm_cmts/api/common/`
  * Compose or inherit in endpoint-specific schemas
* Avoid duplicated fields across schemas.
* Router files must be lean:

  * `router.py` contains routing glue only (APIRouter configuration, endpoint registration, HTTP status translation).
  * No business logic in `router.py`. Business logic must live in `service.py` for that route group (same folder) or a shared service module if reused.
  * Avoid private helper functions in `router.py`. Helpers belong in the service layer.
* Use enums for external contract tokens:

  * API-visible status strings and readiness check identifiers must be enums (not raw strings).
  * Enums must be reused across router, service, tests, and docs.
  * Use `src/pypnm_cmts/lib/constants.py` as the single source of truth for these enums.
* Constants module scope:

  * Only external contract tokens belong in `constants.py` (values that appear in JSON/docs/tests).
  * Internal implementation details (probe dir names, probe filenames, internal subdir tuples) remain service-local unless reused across modules.
* Status code governance reminder:

  * PyPNM `ServiceStatusCode` must remain <= 9999.
  * PyPNM-CMTS `CmtsStatusCode` starts at 10000.
  * Do not add application-level status codes to /ops unless required; rely on HTTP 200/503.

## Tests (Mandatory)

* Every phase deliverable MUST include pytest coverage for new or changed behavior.
* Do not claim a phase item is complete unless pytest has been added and executed
  (or a concrete blocker is documented).
* Tests must not require access to a real CMTS; tests should mock SNMP and device calls.
* Minimum expectations:

  * Settings / config models: defaults, missing keys, validation errors
  * CLI contracts: argument parsing, required flags, error paths
  * Adapters / discovery logic: typed BaseModel outputs, fallback behavior, mocked transport responses
* If a test cannot be written, explicitly state:

  * what is missing
  * why it blocks testing
  * the smallest viable workaround

# FAQ

## Why does `pypnm-cmts serve` exit with "adapter.hostname must be set for snmp discovery"?

PyPNM-CMTS defaults to SNMP discovery mode. In this mode the service must know the CMTS
hostname or IP address, along with SNMP credentials, before startup can complete.

Resolution options:

1) Run with CLI overrides for one-off startup:

```bash
pypnm-cmts serve --cmts-hostname 192.168.0.100 --read-community public --write-community public
```

2) Initialize and persist configuration:

```bash
pypnm-cmts config init
pypnm-cmts config-menu
pypnm-cmts config validate
pypnm-cmts serve
```

You can also preflight your configuration without starting the service:

```bash
pypnm-cmts config validate
```
